# Bojalib — notes for Claude

High-performance .NET 10 library: SIMD/parallel sorting, B-trees, tries, Roaring bitmaps, probabilistic structures.
See `README.md` for the API, `CONTRIBUTING.md` for layout and conventions, `CHANGELOG.md` for what each release contains.

## Status

- 2.0.0 is released (tag `v2.0.0`, on nuget.org). Check `git tag` / nuget.org rather than trusting this file: a
  fresh clone may not have fetched the tags.
- 3.0.0 is being prepared in PR #11; it is not tagged yet. Its breaking changes are listed in `CHANGELOG.md`
  ("Migrating from 2.x") and in `src/Bojalib/CompatibilitySuppressions.xml`. Package validation runs against 2.0.0,
  so any break not in that file fails `dotnet pack`. After 3.0.0 ships, set `PackageValidationBaselineVersion` to
  3.0.0 and delete the suppression file; from then on, 3.x must stay compatible.
- In 3.0.0, from issues #4, #5, #7, #8, #9: `AhoCorasick` (new `Bojalib.Text` namespace), `RangeSet`,
  `FenwickTree`, `CuckooFilter`, `MinHash`; plus `IDictionary` / `ISet` on the B-tree types and `Trie`, and in-place
  set operations, counts and `RemoveRange` on `RoaringBitmap`. #6 (rank/select BitVector) was closed as overlapping
  `RoaringBitmap`. Breaking: `BubbleSort` removed, `HeapSort` / `InsertionSort` internal, `RoaringBitmapBuilder`
  folded into `RoaringBitmap.Create`, `Keys` / `Values` return `KeyCollection` / `ValueCollection`.

## Heavy testing (done in the 2.0.0 cycle)

What exists and where:

- **Scale knob.** `BOJALIB_TEST_SCALE=N` multiplies every CsCheck iteration count (`TestScale.Iterations`) and the
  stress-test sizes. `.github/workflows/long-tests.yml` runs the suite at scale 50 in all four SIMD configurations.
  It runs nightly (`nightly.yml`) and before every release: `release.yml` publishes only if all four jobs pass.
- **Fuzzing.** `Robustness/DeserializerFuzzTests.cs` mutates valid payloads for every `FromBytes`. Each result must
  round-trip or throw `ArgumentException`, within 5 s and 256 MB. It found a real crash in `HyperLogLog.FromBytes`
  (registers out of range), now fixed.
- **Adversarial sorts.** `Robustness/AdversarialSortTests.cs` runs McIlroy's antiqsort adversary, with an
  n log n comparison bound per algorithm, plus NaN, -0.0, infinity and null mixes in every sort.
- **Differential Roaring.** Set operations are compared byte-for-byte with CRoaring (pyroaring); the fixtures are in
  `Fixtures/roaring/setops`, regenerated by `generate.py`.
- **Statistical tests.** `Robustness/StatisticalTests.cs` checks HyperLogLog bias and spread, Bloom and fuse
  false-positive rates, TDigest rank error and Count-Min bounds over many seeds. They stand in for a comparison
  with reference TDigest and HLL libraries, which was not done.
- **Allocations.** `Robustness/AllocationTests.cs` asserts zero bytes where the docs promise it. This found boxing
  in `BTreeDictionary`'s null checks; `ThrowHelper.ThrowIfNull<T>` replaced them.
- **Stress.** `Robustness/StressTests.cs` runs `ParallelSort` at every thread count and concurrently, and long
  random B-tree, Trie and Roaring runs with `Validate()`.
- **Native AOT.** `samples/Bojalib.AotSmoke` is published by CI with `PublishAot` and warnings as errors.
- **Mutation testing.** `eng/mutation-test.sh '**/Sorting/**/*.cs'` runs Stryker.NET; it also runs weekly in the
  nightly workflow, one job per area. Read the caveats in the script:
  - It runs in a throwaway copy that uses VSTest, because the Microsoft.Testing.Platform runner times out.
  - It sets `CsCheck_Threads=1`.
  - It uses `perTestInIsolation` coverage, because `perTest` reports false survivors.
  - Sorting scored 86.4% before the follow-up tests in `Robustness/MutationGapTests.cs`. Most remaining survivors
    are performance-only mutants: the output is still correct, only slower.
  - A Sorting run takes about 1.5 h on 4 cores, which is far too slow for per-PR CI.

Still open:

- Mutation runs for Collections, Probabilistic, Hashing and Text. The workflow is ready; read the reports and add
  tests for real gaps.
- Real hardware: CI now has an `ubuntu-24.04-arm` job for the NEON path (needs ARM runners to be available to the
  repository). 16+ cores (`ParallelSort` scaling) is still only verified indirectly.
- Comparing TDigest and HyperLogLog with reference implementations, beyond the statistical bounds above.

## How to verify (same as CI)

```sh
dotnet format Bojalib.slnx --verify-no-changes
dotnet build Bojalib.slnx -c Release
dotnet test --project tests/Bojalib.Tests -c Release --coverlet --coverlet-threshold 90 --coverlet-threshold-type line,branch --coverlet-threshold-stat Total
DOTNET_EnableAVX512F=0 dotnet test --project tests/Bojalib.Tests -c Release
DOTNET_EnableAVX2=0 dotnet test --project tests/Bojalib.Tests -c Release
DOTNET_EnableHWIntrinsic=0 dotnet test --project tests/Bojalib.Tests -c Release
```

## Measured facts worth remembering

- `AhoCorasick` costs ~3.5 ns per text char regardless of pattern count; the DFA is latency-bound (one dependent
  table load per char). Vectorized `IndexOf` per pattern beats it below roughly 10–100 patterns.
- `Trie` uses 3–5× the memory of `Dictionary<string, T>` for the same keys (1M keys: 160–180 MB vs 37 MB).
- With `--coverlet`, the test suite takes ~3 minutes instead of ~30 s; most of that is the existing `ParallelSort`
  and sorting tests under instrumentation.

## Conventions learned so far

- Probabilistic payloads share a 4-byte header (`Probabilistic/SerializedFormat.cs`: magic, kind, version) and
  their bytes are pinned in `SerializedFormatTests`. To change a format, bump that kind's version and keep a
  reader for the old one; never change bytes under an existing version.

- Measure before claiming performance; put real numbers (and honest regressions) in the docs.
- Every data structure gets a model-based CsCheck test against a simple reference implementation.
- Keep branch coverage comfortably above 90% *without* AVX-512, since CI runners may lack it.
